# 文档协作迭代工作流

本 skill 管**怎么安全迭代文档**（读写边界、版本演化、diff 粒度与确认闸门），与表达风格（`collaborative-rfc-style`）、排版规范（`markdown-conventions`）正交，可组合生效。与 `markdown-conventions` 组合时，**仅要求本次新增/修改段落符合规范，禁止对未涉及章节执行全量 `--fix`**（除非用户明确要求整篇格式化）。设计由来见 [references/decision-log.md](references/decision-log.md)。

## 1. 四条写盘硬契约

1. **原稿只读，新版本落 `_versions/`（兼容 `out/`）**：凡进入文档改写/精修任务（无论是否在 Git 仓库内），默认不得原地覆写原文件，也不主动回写定稿。
    - **输出目录**：若目标目录已存在 `out/` 则沿用 `out/`；否则默认新建同目录 `_versions/`（Obsidian 可在 `Excluded files` 中排除 `/_versions/`）。若基线本身已在版本目录内，新版本写到同级目录，禁止套娃（如 `out/out/`）。
    - **命名规则**：无版本号基线 → `<原名>-v1.<ext>`；已有版本号（`-vN` / `-改N` / `-vN.M`）直接递增；若从旧版本分叉（如基于 `v2` 改而目录已有 `v3`）则用 `v2.1`。
    - **原地修改豁免**：仅在用户明确指令“原地改 / 直接改这个文件 / 定稿回写”，或属于轻量单次维护（修错别字、改单条配置、改代码仓 `README.md` / `SKILL.md` 且目录中无版本目录）时原地修改。
2. **唯一修改基线**：目录中存在多个历史版本或草稿时，严格以用户点名的文件为唯一基线。**允许仅列目录文件名以确定下一个版本号，禁止读取并混入非基线文件的内容**。若用户显式指定参考稿（如“参考 A 的结构改 B”），明确区分基线稿与只读参考稿；若未指明基线文件，先确认再动笔。
3. **局部最小 diff，禁止擅自重写**：除非用户明确要求“重写”或“大改”，否则保持未涉及章节逐字不变，仅对目标段落做最小范围修改。落盘新版本时，**必须先复制基线文件到目标路径，再用局部编辑工具修改目标段落，落盘前用 `diff` 校验非目标段落零改动**（避免全文写出引入隐性润色）。
4. **先议后写**：用户提问“有什么建议 / 怎么改 / 会不会太…… / 帮我看下 / 评审下”时，只读输出诊断、方案或可选改法，**不直接改盘**，待用户拍板后再写入。反之，若用户已给出明确改法或已拍板方案，直接落盘，不重复确认。

## 2. 动笔前的边界对齐

在生成或大改正文前，仅在以下关键约束缺失且会显著导致返工时简短确认（最多 1–2 个问题），否则按最小改动直接处理：

- **交付载体与篇幅上限**：例如口播时长（按语速折算字数）、Word/表格单元格高度、PPT 页数，避免先铺开长文再反复砍字。
- **呈现形态**：自然段落、对比表格、结构化要点还是流程图。
- **叙事顺序**：例如汇报类常用的“背景 → 效果 → 过程”还是“问题 → 方案 → 验证”。
- **联动文件范围**：若目录中同时存在主文档与衍生稿（如逐字稿、摘要），明确本次只改哪一份，不擅自顺带改另一份。

## 3. 典型场景执行路径

| 场景 | 默认动作 | 禁止行为 |
| --- | --- | --- |
| 评审 / 提建议 | 只读目标文档，按问题级别与具体位置输出诊断表 | 顺手把原文件改掉；跨读历史旧稿混评 |
| 局部改写 / 调措辞 | 意图开放时先给 1–3 个候选改法，确认后（或用户已给明确改法时）复制基线并局部替换目标段落 | 全文重写引入隐性润色；覆盖原稿 |
| 调结构 / 补图表 | 保持原文正文不变，仅在指定位置插入衔接句、表格或图示 | 借机润色或删减原文内容 |
| 衍生稿生成（逐字稿、自评） | 优先读取真实载体模板或时长约束，先给预览再落盘 | 忽略载体限制直接生成超长通用稿 |

## 4. 落盘后汇报格式

每次写盘完成后，回复中交代清楚以下信息：

- **写入路径与基线**：基于哪个文件（保持未改），写入了哪个新版本文件。
- **变更明细**：按章节或条目说明具体增删改了什么，让用户无需逐行肉眼 diff。
- **未动范围确认**：基于 `diff` 确认其余章节或关联文档未做改动。
