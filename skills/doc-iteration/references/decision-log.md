记录 `doc-iteration` skill 确立当前边界的依据，供后续迭代时核对。

## D1 为什么从全局规则抽成独立 Skill（2026-11-21）

- **背景**：复盘 `转正述职2026-` 全部 13 个会话（83 轮 Prompt）发现，“不要改原文 / 在 `out/` 输出新版本 / 仅基于指定版本改 / 不要重写只改写”这类写盘边界被口头重复强调了 9 次，并多次触发原稿回滚。
- **决策**：不把该契约常驻 `~/.gemini/GEMINI.md`，而是独立为 `doc-iteration` skill。
- **理由**：
    1. 全局规则每次对话无条件加载，代码开发或排查任务不需要 `out/` 文档版本化语义，放在全局既增加噪声也有误触发风险。
    2. 将“怎么迭代（`doc-iteration`）”“怎么表达（`collaborative-rfc-style`）”“怎么排版（`markdown-conventions`）”正交拆分，普通文档迭代与 RFC/述职写作都能按需复用，避免多个写作 skill 重复维护写盘流程。

## D2 四条硬契约的实测来源（2026-11-21）

- **原稿只读 + `out/` 递增**：多次会话中漏说一句“输出到 `out/`”即导致原稿被覆写，后续不得不额外耗费数十步回滚。
- **唯一基线**：目录存在多个 `-vN` 版本时，若不限定基线，模型会自行把旧版内容混回当前版本。
- **局部最小 diff**：模型在格式或顺序调整时倾向全文润色重写，导致用户无法判断哪些核心事实被改动。
- **先议后写**：纯讨论态会话（只读出方案、人工拍板再落盘）返工率远低于直接改盘。

## D3 评审加固：目录策略、工程防线与跨 Skill 裁决（2026-11-25）

- **默认目录由 `out/` 迁至 `_versions/`（向后兼容 `out/`）**：
    1. 用户高频在 Obsidian 中使用，`_versions/` 可在 `Excluded files` 中统一排除，消除历史稿对全局搜索、Quick Switcher 和反链的噪声，同时在文件树里保持可见、便于并排对比。
    2. 避免在代码仓库中与构建产物目录 `out/` 撞名；已存在 `out/` 的老目录直接沿用，零迁移成本。
- **按“任务形态”而非“是否在 Git 仓库”划定豁免**：多轮文档打磨时每轮 commit 不现实（打断思路、不便并排比稿），即使在 Git 仓内也默认走版本目录，定稿后再做一次干净提交；仅轻量单次维护（修 typo、改 `README`/`SKILL.md` 等且无版本目录）原地修改。
- **`cp + 局部编辑 + diff` 防线**：防止模型用全文写盘时顺手对未涉及段落做隐性润色，同时让“未动范围确认”有实测依据。
- **与 `markdown-conventions` 的冲突裁决**：组合生效时只要求改动段落符合规范，禁止对未涉及章节执行全量 `--fix`，避免因历史 lint 报错击穿最小 diff 契约。
