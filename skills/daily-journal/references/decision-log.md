## 需求与边界（2026-09-16 立，不随迭代变）

用户原话：「我想要设计一个记日记的 skill，我可以随时触发笔记，并帮我更新到每天的日记中，不改变我的内容，但是你需要进行分类和关联，告诉我你是怎么设计的。」拆成四条硬要求：

| 编号 | 要求 | 含义 |
| --- | --- | --- |
| R1 | 随时触发 | 任意时刻用自然语言触发一次捕获 |
| R2 | 更新到当天日记 | 内容落到当天那一篇日记文件 |
| R3 | 不改变我的内容 | 原文逐字保留，不改写、不润色、不重排（射程与例外见硬规则 1） |
| R4 | 分类与关联 | 由 agent 补充结构与链接，且与原文分离 |

**本 skill 的边界（有意不做，非遗漏）**：不动 `### 关联笔记` 的 dataviewjs 与 `Scripts/x.js`；不批量回填历史日记；不做中文别字检测（D8）；本阶段只启用关联通道 1（D2）；待办不路由到 `10-GTD/*`（D23）；不写其他笔记、不新增 tasks 查询块（D23）。

**已由前置事实解决、不再作为决策项**：新建日记的落点（平铺 vs `02-Done/YYYY-MM/`）由 `obsidian daily:read` 服从 `.obsidian/daily-notes.json`，无需自定义；Obsidian 未运行时的策略是中止并提示、不静默回退（硬规则 5）。

vault 侧的事实（日记目录 / 命名格式 / 模板 / dataview 关联规则 / CLI 行为实测）不记在本文，见 `references/vault-conventions.md`；当年的核对原稿在 vault 迭代页的 `工程记录.md`。

## D1 · 派生层位置

- **结论**：派生层固定为独立的 `## 今日分类与关联` 区块，位于 `## 今日的思考` 之后、`### 关联笔记` 之前。
- **背景**：分类与关联属于机器产物，必须与用户原文物理隔离，以满足 R3「不改变我的内容」。
- **备选**：A 独立区块；B 每条原文后紧跟 `> [!jc]` callout（就近可读）。
- **未采纳 B 的原因**：会把非用户书写内容插进原文区，只能靠标记界定边界；原文区不再是逐字原文。
- **落点**：`SKILL.md` 的写入位置；`journal_apply.mjs` 的 `SECTIONS`。

## D2 · 关联通道 2

- **结论**：本阶段只启用通道 1（日记内 wikilink）；通道 2（写入 `09-Note4LLM` 主题笔记的 `## YYYY-MM-DD`）只保留设计，关闭。
- **背景**：通道 2 会修改其他笔记，属跨文件副作用。
- **备选**：本阶段启用；本阶段关闭。
- **关闭原因**：`## 日期` 标题在现有库中的语义是「那天学到的东西」（如 `09-Note4LLM/6min.md`），随手记不一定适配；先跑顺零副作用的通道 1。
- **重开条件**：通道 1 稳定使用后评估，且需用户显式开启。
- **落点**：`SKILL.md` 的硬规则 4（不碰其他笔记）。

## D3 · 落盘方式

- **结论**：默认 `dry-run`，只展示将要新增的文本（diff）；需显式 `--write` 确认才落盘。
- **背景**：误写当天日记的代价高于多一次确认。
- **备选**：默认直接写；默认 dry-run。

## D4 · 原文时间戳

- **结论**：不往原文插入任何时间前缀。捕获时间只存于标记块 `id`（如 `20260916-1432-a1f3`）与派生层表格的「时间」列。
- **背景**：往原文行首插入 `14:32` 即属修改用户内容，与 R3 冲突；一次捕获多行时前缀位置有歧义；与现有 `09-Note4LLM/6min.md` 按天分组、条目无时间的习惯不一致。
- **备选**：原文行首加 `HH:mm`；仅在派生层记时间。

## D5 · 不确定就问

- **结论**：分类与写入流程中任何一环拿不准，**先问用户确认**再落盘；`#unsorted` 只是占位，不是终点。
- **背景**：分类词表再确定也无法覆盖全部情形；静默猜测一旦落盘，纠错成本高于一次提问。
- **备选**：A 不确定即静默降级 `#unsorted`；B 不确定就当场问用户。
- **未采纳 A 的原因**：`#unsorted` 会被忽略，等于把不确定性藏进数据；而且用户无从知晓 agent 曾经犹豫过。
- **重开条件**：这是硬规则；除非用户显式要求全自动（不再逐条确认），否则不关闭。
- **运行表述**：`SKILL.md` 硬规则 3。
- **2026-09-18 补**：D5 从「自觉遵守」升级为「机械强制」—— 词表外的新标签，不带 `--allow-new-tag` 就直接退出 1、不落盘（见 D9）。规则不再依赖 agent 的自觉。

## D6 · 校对是独立的一步，且只能机械执行

- **结论**：捕获流程中增加一层「校对」，但它是**独立的、用户逐条确认的机械替换**步骤，不是写盘时的隐式润色。`--proofread` 只读不写；`--fix` 在写入时生效，且修正由脚本做字符替换。
- **背景**：用户要求「检查输入的准确性，如果可以，进行修正」。这与硬规则 R3「原文不得擅自改写」表面上冲突：R3 说 skill 不能动用户的话，修正就是要动。
- **备选**：A 放弃，严守 R3；B 允许 agent 顺手改错；C 拆成独立步骤 + 机械替换；D 只报告不改。
- **未采纳 A / B 的原因**：A 无法满足用户诉求；B 里「顺手改」正是 R3 要防的 —— 模型一旦有润色权，原文就不再是用户的原文。
- **未采纳 D 的原因**：用户明确要求「如果可以，进行修正」。
- **结论细化（两级）**：
    - **无损**（行尾空白 / 重复虚词 / 大小写规范）可 `--fix=safe` 批量套用；
    - **改字**（`ascii-typo`）必须逐条确认，或用户显式 `--fix=all`。
- **运行表述**：`SKILL.md` 硬规则 6 与工作流第 2 步。

## D7 · 字词判定的词表与阈值

- **结论**：词表用 **155 个注册表词**（非 1161 个白名单笔记名）；`ascii-typo` 只放行两类：**len ≥ 7 允许 Damerau 距离 2**，**len 5-6 仅允许单次相邻换位**。
- **背景**：先用笔记名做词表，在真实文本上 6/6 误报（`代理→管理`、`尝试→面试`、`skill→shell`），因为笔记名全是日常词。改用注册表后，编辑距离近邻仍有约一半误报（`none→done`、`gate→date`、`team→term`）—— 领域词本身就是常见英文词。
- **备选**：A 不查拼写；B 只查大小写；C 保留全部近邻匹配。
- **未采纳 C 的原因**：错改的代价远大于漏报；且高噪声会让用户直接忽略整个功能。
- **落点**：`journal_apply.mjs` 的 `buildVocabulary()` / `isTranspositionOnly()`。

## D8 · 中文别字检测不做（实测否定）

- **结论**：**不实现**中文别字检测；连同 `common-chars.json` 与 `tools/build-common-chars.mjs` 一并移除。同理不做 `[[` / `]]` 成对检查。
- **背景**：曾实现一版「同长度、一处替换 + 错字窗必含生僻字 + 不跨正确词边界」的中文滑窗检测。全库实测：3.83M 字上给出 9567 条（5.06 条/千字）。穷举 3070 个不同错字窗，**0 个**在语料中出现 0 次（1125 个出现 1-2 次，1142 个 3-10 次，803 个 11+ 次）—— 因为窗口就是合法长词的子串（`笔记整` 是 `笔记整理` 的子串）。细节见 vault 工程记录。
- **备选**：A 保留并降低召回；B 上分词器/词典；C 删掉。
- **未采纳 A 的原因**：降不到可用水平；B 引入外部依赖且在个人语料上仍不可靠。
- **可重开条件**：引入可靠的中文分词器 + 个人词典，且能把全库密度压到 0.5 条/千字以下。
- **`[[` / `]]` 同理**：全库 111 处全是误报（`[[白话解析] Flink…](url)`、Python 的 `[1]]`），正则分不出 markdown 链接文本与代码。

## D9 · 分类的载体是真标签

- **结论**：分类写成**库内真实的多级 Obsidian 标签**（如 `#work/sales`、`#work/sales #work/shops`），**不加反引号**；不再写 `work/sales` 这种纯文本。
- **背景**：最初设计把分类写成「域/锚点」文本，落进「分类」列后既不是标签（检索不到），也不是链接（点不动）—— 它只是一段死字符串。
- **备选**：A 保持文本；B 用反引号包裹（当作行内代码）；C 裸标签。
- **未采纳 A / B 的原因**：反引号里的分类在 Obsidian 中**不是标签**，只是行内代码。分类的意义就在于能被检索、能被聚合，只有裸标签做得到。
- **代价**：词表从「一个闭集」变成「骨架 ∪ 库内实时标签」，判定不再是纯查表；已用 `--allow-new-tag` 机械闸门兜住 D5。
- **落点**：`journal_apply.mjs` 的 `loadTags` / `suggestTags` / `validateTags`；`--migrate-tags`（11 条历史行已迁移）。

## D10 · 事后改写原文是 R3 的显式例外，且必须由脚本机械执行

- **结论**：新增 `--fix-written --id=<块id> --replace='错→对'`。它是 R3「原文不得擅自改写」里**用户起意**的那条例外，由用户在 2026-09-18 显式授权（「错词改吧」）。四条约束缺一不可：① 只能由脚本做字符替换，**模型永远不产出最终文本**；② 必须用 `--id` 限定到具体块，命中次数不符即拒绝；③ 只能落在 `jc:begin` / `jc:end` 之间；④ 它**不走** R3 的两条校验（`bodyExact` / `originalsPreserved` —— 那两条只守「追加」路径），而是换上一套等价守卫（反向回代 + 块外逐字节不动 + 命中数）。**这是换岗，不是放宽。**
- **背景**：用户的错字是**拼音同音词**（`便宜`→`漂移`、`系统出`→`系统里`），编辑距离类方法根本抓不到（D8 已实测否定中文别字检测）；只能由人指认、由脚本执行。
- **备选**：A 严守 R3，一律不改；B 允许 agent 直接改；C 脚本机械改 + 人工指认 + 逐条确认。
- **未采纳 A 的原因**：用户明确要求能改。
- **未采纳 B 的原因**：「顺手改」正是 R3 要防的 —— 模型一旦有权改写，原文就不再是用户的原文。
- **配套守卫**：反向回代（把「对」再换回「错」必须逐字节还原，专门拦右值在原文中也出现的情形）、块外逐字节不动、命中数校验 —— 实现细节见 vault 工程记录。
- **为什么 `--id` 是必须的**：日记里存在**合法**的「便宜」用法（`02-Done/2026-09-38w-18.md` 的「我妈确实贪小便宜」）。不带 `--id` 的全局替换会把用户的原话改坏。
- **改动正文必须重算 id**：id = `sha1(正文)` 前 4 位，改字即失效，因此 `jc:begin` / `jc:end` / 索引行三处 id 同步重算（正文本身不再二次改动）。
- **运行表述**：`SKILL.md` 的「事后修正」一节。
- **口径修正（2026-09-20）**：R3 由「原文逐字不改」改称「**原文不得擅自改写**」。原标题是一个**字节**断言，容易被读成「任何改写都违反」，与同一份文档里早已存在的 `--fix-pair` / `--fix-written` 自相矛盾；改后是一个**权限**断言 —— 拦的是「擅自」，不是「字节」。同时明确两条通道的性质不同：`--fix-pair` 是默认流程里的**闸门**，`--fix-written` 是**例外**。

## D11 · id 自洽性是体检报告，不是法律

- **结论**：提供 `--verify-ids`（只读，不一致时退出 1；`--write` 可修复）。但**不**把「原文与 id 必须自洽」写成硬规则，文档必须写明旧 id 是**线索，不是错误**。
- **背景**：曾在设计文档里写「原文与 id 必须自洽」，被用户否决：「我有可能改写旧的日志，这个限定不就是卡死了吗？」
- **理由**：id 是 agent 生成的**不透明锚点**，不是用户写的内容。用户手改旧日志（在本 skill 之外的操作）会让 id 过期，这是**正常**的。
- **备选**：A 硬规则，不一致即报错中止；B 只做诊断，可选运行。
- **未采纳 A 的原因**：会把用户的正常行为判成错误；而且一旦中止写入，就没法继续记了。
- **用法定位**：`--write` 修复时**只重写 id 字符串**，正文逐字节不动；修复前用反向替换断言，还原不回去就中止。
- **运行表述**：`SKILL.md` 的「自检」一节。

## D12 · 索引表头叫「块 id」，不叫「原文锚点」

- **结论**：派生层表格表头为「时间 · 块 id · 分类 · 关联」；文档、脚本建表常量、以及 3 个已有日记文件一并改名。
- **背景**：「锚点」在本项目里已经是**分类词表的专门术语**（`分类词表.md` §六 的「锚点」列）。再拿它称呼标记块 id 会撞名，读者无法区分「锚点」指的是词表条目还是 `20260916-1432-a1f3`。
- **备选**：A 保持「原文锚点」；B 改成「块 id」。
- **未采纳 A 的原因**：一词两义；而且脚本里本来就管它叫「块 id」（`--fix-written --id`）。
- **落点**：`journal_apply.mjs` 的建表常量与 2 处注释、`references/vault-conventions.md`、真实日记 `02-Done/2026-09-38w-{16,17,18}.md` 各 1 行。
- **执行方式**：日记文件不是手改的，走「备份 → `expectBefore` 乐观并发 → 读回校验」；再用独立 `diff` 确认每个文件**只变 1 行**（字节 −6）。

## D13 · registry.json 只输出脚本真正读的字段

- **结论**：`registry.json` 只保留 `version` / `generatedFrom` / `anchors` / `tagSkeleton` 四个字段；`domains`、`domainPaths`、`catchAll`、`whitelistRoots`、`leaves` 一律不再输出。
- **背景**：这五个字段由生成器写出，但 `journal_apply.mjs` 对它们的读取次数**全为 0**。它们是「路径推导分类」时代的遗迹 —— 那套机制已被 D9 整体替换。
- **判据**：**生成了却没人读的数据，一律删。** 留着会误导下一个人（或下一个 agent），让它以为分类还看路径。
- **注意**：生成器里的 `DOMAIN_PATHS` / `CATCH_ALL` **常量不删** —— 它们还负责「给出 9 个一级标签的名字」和「校验文件夹真实存在」，属于构建期校验，不是输出。
- **校验方式**：删后重新生成，`anchors` 与 `tagSkeleton` 与改造前**逐字节一致**。

## D14 · 文档同步：快照只追加，规格必须改

- **结论**：分两类处理。**快照类**（迭代页的实测记录、本文的「沿革」）→ 只追加带日期的追补，**正文不改** —— 它们是「当时查过什么、当时怎么做的」的证据。**规格类**（`SKILL.md`、`references/*`、`分类词表.md`）→ **必须改到与实现一致**。
- **背景**：口径变更后逐处核对，发现改动会同时污染两类文件：规格不改会误导，快照改了就毁掉证据。
- **附带纪律**：vault 内的 `.md` 里举标签例子**必须裹反引号** —— 裸标签会被 Obsidian 当成真标签；围栏代码块内不解析，除外。

## D15 · skill 必须自包含：生成器随 skill 分发

- **结论**：`build-registry.mjs` 搬进 skill（`<skill>/tools/`），随 git 仓库分发。vault 里那份已删。
- **背景**：发现一个真实缺口 —— 生成器以前**只**存在于 vault 的项目文档目录，而 vault 不是 git 仓库。于是「skill 在 git 里，skill 的上游工具不在」：改生成器没有历史、回不去，而 `journal_apply.mjs` 找不到它就退出 3。
- **备选**：A 保持现状（工具留 vault）；B 搬进 skill，vault 副本删掉；C 搬进 skill，vault 副本保留并提示。
- **未采纳 A 的原因**：skill 依赖一个不在版本控制里的文件，这本身就是缺陷。
- **选 C 的原因（后于 2026-09-18 收尾为 B）**：两份共存但**不静默择一** —— 明确用 skill 自带的那份，并把「副本已忽略」写到 stderr。两份悄悄分叉比只有一份更糟。
- **连带改动**：词表路径改为三级解析（`--taxonomy` > 脚本旁边 > `--vault-root` 下搜，要求唯一）；`--out` 默认值改为 `<vault-root>/.daily-journal/registry.json`；`--rebuild-registry` 重建后直接退出 0。
- **影响**：`SKILL.md` 的 registry 一节；`references/registry.template.json`。

## D16 · 分类词表是库级基础设施，不再是项目文档

## D17 · 中文错别字由模型识别，但只准「出对」，执行仍由脚本（2026-09-18）

- **背景**：用户要求「帮我识别一轮错别字，我发现你没改会提示你」。机械校对**查不了中文别字** —— `cjk-typo` 已被 D8 实测否决，`ascii-typo` 只管英文词；而用户实际犯的正是同音字（`便宜`/`漂移`、`系统出`/`系统里`），字符距离法从原理上抓不到。
- **结论**：把中文别字的**识别**交给模型，但**执行不放宽** —— 模型输出「错→对」对与理由，**永不产出最终文本**，替换由脚本做（与 D10 同一条约束）。
- **通道**：新增 `--fix-pair='错→对'`。缺的不是权限是**通道**：`--proofread` 找不到中文别字，`--fix=fN` 只认脚本自己找到的条目 id（`applyFixes` 按 `findings` 的 `start`/`end` 偏移切片），`--replace` 又只长在事后的 `--fix-written` 上。
- **守卫一字不省**：每对必须命中，命中 0 次不是「跳过」而是**报错退出**（那说明模型读错了原文）；反向回代必须逐字节回到原文。顺序上 `--fix-pair` **先于** `--fix`，因为模型读的是**原始文本**。
- **明确不动的东西**：`的地得`、口语化写法、生造词、专有名词、中英混排。那是品味，不是错 —— 动了就滑向润色。
- **代价（必须承认）**：模型的判断**不可复现**，同一句今天报明天可能不报。因此机械守卫是这套设计唯一的支点，不能省。
- **反馈环是双向的**：漏报 → 事后走 `--fix-written`；**误报（把对的改成错的）→ 更要立刻回滚**。误报比漏报严重。
- **运行表述**：`SKILL.md` 第 2 步与硬规则 1。

## D18 · 静默失效比崩溃更难发现，验收必须钉住「真的做了」（2026-09-20）

- **背景**：一轮审查报出四个 P0（`--audit`、`--migrate-tags`、空内容、`--fix`）。共同点不是「崩了」，而是**不报错、不抛异常，只是静默地什么都不做**：`--audit` 搜的字面量 `unsorted/-` 在派生层里从不出现（那边写的是 `#unsorted`），于是它**永远返回 0 行却一路显示正常**；`--migrate-tags` 不认 `--allow-new-tag`，同一条 D5 规则写盘入口放行、迁移入口一律拒绝；`bodyExact` 用 `indexOf`，而 `indexOf("") === 0` —— **空串恒真**，空内容混过了五项校验；`--fix` 把去重做在检测循环里，同一个词只改第一处，后几处静默漏掉。
- **结论**：这类缺陷的验收不能是「跑通了、没报错」，必须是**「真的做了」**。三条口径固定下来：① 每个模式都要有一条**能观察到输出**的验收 —— `--audit` 这条必须造出含占位标签的夹具才验得出来，否则「0 行」和「坏了」长得一模一样；② 凡是 `indexOf` / `includes` / 空集合比较，都要单独问一句「空值时会怎样」，**「恒真」型守卫**是最隐蔽的一类；③ 同一条规则有多个入口时（写盘 vs 迁移），**口径必须一起改**，只改一个等于制造分歧。
- **不新增决策项**：四条都是修 bug，没有引入新机制。记在这里是因为**「怎么验」本身是决策** —— 它决定了下次同类缺陷能不能被抓住。
- **落点**：`journal_apply.mjs`（`--audit`、`--migrate-tags`、空内容两层拦截、`--fix` 的 `spans` 全量替换）；缺陷细节见 vault 工程记录。

## D19 · 待办独立成层，不受 R3 约束

## D20 · `jt` 区整节单区，不带 id

- **结论**：待办区用一对**无 id** 的 `<!-- jt:begin -->` / `<!-- jt:end -->`，所有待办行平铺其中。不采用「每次捕获一个带 id 的块」。

- **判据（一句话）**：是「现在是什么」→ 仓库；是「为什么、怎么试的、还没定」→ vault。
- **定稿即提**：一条口径定稿就搬进仓库（决策 → 本文 D 系列，编号一次分配、**永不重排**；实现口径 → `SKILL.md` 或 `vault-conventions.md`），并把 vault 侧那段的**结论正文删掉、压成指针**。不攒到迭代结束批量做（批量必漏，中间期两边都在长）。
- **为什么不能两边同存结论正文**：此前仓库头部写着「上游权威：vault `04-决策记录.md`」，而那份又自称「唯一权威口径」—— 两边互指，于是同一条决策必须写两遍，2026-09-21 因此收口过一次。**vault 不在 git 仓库里**（误删只有 File Recovery 一条路），所以不可重建的东西（决策条文、验收证据）一律留在 git。
- **工程史去哪**：实现口径、缺陷修复、事故、验收证据与复现方式 → vault 迭代页的 `工程记录.md`（原始记录，含当时的口径表述）；仓库侧不再复述数字，「当时怎么验的」去 vault 查。判据：**读它是为了「做」→ `SKILL.md`；为了「定」→ 本文；为了「信」→ vault 工程记录。**
- **新开一轮迭代**：在 vault 建 `09-Note4LLM/productivity/projects/<YYYYMMDD>-<主题>/README.md` 当迭代页，仓库侧零准备动作。迭代收口时把批次账写进 vault 的 release note；未完成的跨迭代项转进 `10-GTD/me.md`。
- **落点**：`SKILL.md` 末节「维护本 skill：迭代工作区与上提」。

## D28 · 派生层「块 id」列写成别名块链接（2026-09-20，原 C12）

- **结论**：索引行的「块 id」列写成 `[[<笔记名>#^<块 id>\|<块 id>]]` —— 别名就是 id 文本（列里仍读得出 id，不写别名 Obsidian 会渲染成「笔记名 > 块 id」，这一列被撑得极长）。不用 `↩` 别名（整列变成一排箭头，读不出哪行对应哪个 id）；不用裸 `[[#^id]]`（行被剪到别的笔记里就哑了）；**不能裹反引号**（代码段里的 `[[…]]` 不进链接表，点不动）。
- **背景**：用户要求「分类的块 id 能不能也加上链接」—— 这一列原是不透明的 opaque id，看得见、点不动，要找那段思考还得自己拿 id 去搜。
- **连带口径**：链接里带 `\|`，所以**解析侧一律按未转义的 `|` 拆列**（Node 侧 `splitUnescapedPipes()`，Obsidian 侧 `AUDIT_PAYLOAD` 内联同口径）。硬用 `split("|")` 会让列序号整体后移 —— `--audit` 的 `cells[3]` 就不再是分类列，那些行**被悄悄丢掉**（D18 同类）。
- **边界**：只认索引行；`## 今日待办` 里用户自己的 `[[…#^id|↩]]` 不被牵连。**已知缺口**：待办出处链接不会跟着 id 重算，块 id 变了它就指向空处（暂不自动改）。
- **历史笔记**：用 `--link-block-ids` 回填（默认 dry-run），只改 id 那一格；块不在本文件报 `block-missing`，块没尾锚点报 `anchor-missing`（先跑 `--add-anchors`）。
- **运行表述**：`SKILL.md` 的「迁移派生层的块 id 成块链接」一节。

## D29 · 待办出处标记是别名块链接，位置在描述末尾、emoji 字段之前（2026-09-20，原 C9）

- **结论**：提取出的待办默认带一个来源链接，形如 `[[2026-09-38w-20#^20260920-2000-a1b2|↩]]`，**写在描述末尾、emoji 字段之前**：

    ```text
    - [ ] 交房租 #family [[2026-09-38w-20#^20260920-2000-a1b2|↩]] ➕ 2026-09-20 📅 2026-09-21
    ```

- **为什么不用 `<!-- from:<块 id> -->` 注释**：注释能活命（Tasks 字段照解、渲染不显形），但**点不动** —— 实测写在 `<!-- -->` 里的 `[[…]]` 不进链接表（同一篇里注释内、注释外各放一条指向同一个块锚点，metadata cache 只登记外面那条）。注释还有个更隐蔽的问题：**行尾必须是字段**，行尾挂上 `-->` 之后 Tasks 的字段正则（`/➕️? *(\d{4}-\d{2}-\d{2})$/` 一类，锚定行尾）一个都匹配不上，`createdDate` 直接是 `null`，这条待办从「今日创建的任务」里消失。库里就躺着一条现存例子：`- [ ] fzy 和 fzf 的区别 ➕ 2026-06-25 】`。
- **为什么要带笔记名**：`[[#^id]]` 是**同文档**引用，而待办落当天日记、来源块可能在别的日子。
- **局部局限**：脚本只核对链接里的笔记名（`wikilink-missing`），**不核对块 id** —— 块 id 写错就是一个悄悄指向空处的链接。它证明不了提取对不对，只回答「这条待办是哪句话来的」。
- **范围**：V1 只提案或按 D26 落盘，**不路由到 `10-GTD/*`**（D23）；不改脚本；不改视图层。
- **运行表述**：`SKILL.md` 的「待办提取」一节。

## D30 · 关联列只链原文点名的实体（2026-09-20，原 A1–A4）

- **结论**：四条口径，合起来是一句话 —— **标签是主题，链接是实体**。
    - **只链原文里实际点名的实体**，库里有对应笔记就链上；`--classify` 给的候选路径只是「库里可能有对应笔记，核对一下」的提示，**不是填充项**（词面命中 ≠ 实体关联）。实测反例：一条讲带娃的思考命中 `#family/🐱`、`#family/🐷`、`#life/健康` 三个候选，链上去就是三条噪声。
    - **留 `—` 的合法理由是「这条没有对应实体」**，不是「懒得想」；反过来也不为了不留空硬链（**文件存在 ≠ 这条内容在讲它**）。
    - **目标必须真实存在，由脚本机械保证** —— `--links` 按 Obsidian 的解析规则（全路径带/不带 `.md`、文件名、frontmatter aliases）解析不到就**退出 7**，dry-run 阶段就拦。这与「分类标签可以新建、不需要有文件」不矛盾。
    - **不回溯**：只管新捕获与用户点名要改的那一条；已写完的历史条目与索引行一律不动。
- **背景**：用户口径「如果日记关联到某个文件，这个文件的链接都放在关联中」「没有实际文档，关联就没有意义」。
- **运行表述**：`SKILL.md` 硬规则 7。

## D31 · 词表读取范围与剔除口径（原 T3 / T4）

- **结论**：词表实时那半只读 **5 个目录** —— `00-InBox&FleetNote` / `02-Done` / `09-Note4LLM` / `10-GTD` / `11-Knowledge`；`--scope=` 可覆盖。机械剔除三类：`#gtd` / `#gtd/*`（任务状态，不是主题）、纯数字（GitHub 标题 `· Issue #2672 ·`）、单字符（代码/链接噪声）。**其余合法即允许，包括新建。**
- **背景**：`101-LiteratureNote` / `102-PermanetNote` 经用户确认**不包括**（实测差异只有一个标签 `#心理结构`）；`04-OnlyWork` / `08-Learning` / `Evernote` / `999-待整理` 属「其他用途，待整理后整合」，本阶段不纳入。用户明确表示**暂不**只读引入 `04-` / `08-`，因此**以新建标签为主**。

- **为什么允许新建**：这是标签相对「文件锚点」的核心好处，也是「不放封闭配置」的必然结果；边界由 `validateTags()` 在写盘前机械校验（D9 的 `--allow-new-tag` 闸门）。
- **落点**：`build-registry.mjs` 的目录常量；`journal_apply.mjs` 的 `--tags` / `--scope`。

## D32 · wikilink 按 Obsidian 的真实规则解析（原 P6）

- **结论**：链接合法性用 `app.vault.getFiles()` + `app.metadataCache` 建索引来判：全路径（带/不带 `.md`）、文件名（basename）、frontmatter `aliases`。`[[#标题]]` / `[[#^块]]` 是合法的**同文档引用**，只有真正的 `[[]]` 才算空链接。
- **背景**：只比对文件名会产生大量误报（`[[08-Learning/LLM/01-LLM|LLM]]` 是合法路径式链接）。
- **附带**：链接区间内的内容不参与拼写检查 —— 否则 `[[02-Done/…]]` 里的 `Done` 会被报成大小写错误。
- **落点**：`journal_apply.mjs` 的 `parseWikilinkTargets()` 与 `--proofread` 的检查项。

## D33 · 新增检查项必须把误报密度重测一遍（原 P8）

- **结论**：误报密度是验收指标。任何新增检查项，必须把三档数字（全库 / 扣掉旧笔记既有行尾空白 / 用户真实捕获文本）重新测一遍并记录（原基线：全库 5.06 条/千字 → 改后 0.34，真实捕获 0）。
- **背景**：一个 5‰ 精度的检查只会训练用户忽略它（D8 的教训）。
- **落点**：`--proofread` 的检查集合；实测数字与复现方式见 vault 工程记录。
