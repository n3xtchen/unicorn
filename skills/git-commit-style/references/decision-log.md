# Skill 创建与迭代记录

本文档记录 `git-commit-style` 的设计决策，供后续根据仓库新历史迭代，不是每次提交的运行日志。

## 2026-09-01：初始边界

目标是根据当前仓库的中文提交历史，生成、改写或评审符合项目习惯的 Commit 信息，而不是强行套用统一模板。

## 设计决策一：仓库历史优先

生成建议前优先查看近期提交，按目标模块和近期中文提交归纳：

- type；
- scope；
- 动作词；
- 技术名词写法。

不把纯英文历史机械当作中文风格依据，也不为了中文而翻译稳定的技术标识。

## 设计决策二：默认 Conventional Commit + 中文描述

默认格式为：

```text
type(scope): 中文动作描述
```

描述末尾不加句号。仓库如果同时使用中文前缀格式和 Conventional Commits，优先参考近期、目标模块更常见的形式。

## 设计决策三：不擅自提交

用户要求生成或评审 Commit 信息时，默认只提供文案，不自动执行 `git commit`。如果用户明确要求提交，仍需先检查变更范围、暂存区和测试结果。

## 设计决策四：提交范围必须先可见

变更依据不足时先查看 `git diff --cached`、`git diff` 和路径状态，不编造 scope 或变更内容。相关变更应尽量一个 Commit 表达一个可评审的目的；彼此独立的动作应建议拆分。

## 2026-09-03：正文优先承载多点变更

用户明确偏好：当一个提交包含多个紧密相关的具体修复时，标题可以保持概括，但提交正文应明确列出各项变更，避免仅使用“收口边界”一类信息量不足的标题。默认正文通常列出 3～5 个具体点；不把所有细节强行压缩进单行标题。

## 2026-09-05：Commit 正文必须使用真实换行

用户发现提交正文中的 `\\n` 被作为普通字符写入 Commit，导致 `git log` 显示字面量 `\\n`。因此执行提交或 amend 时，必须使用真实换行（推荐 quoted heredoc 或独立 message 文件），禁止通过普通字符串拼接 `\\n`；提交后还必须检查 `%B` 输出并确认不存在字面量 `\\n`。

## 后续迭代规则

- 新增稳定的中文提交风格时，在本文档追加“设计决策”或“修正记录”；
- 用户明确修正的偏好优先于旧示例；
- 只记录已确认的规则，不把一次临时文案当成全局风格；
- 不记录隐藏推理或敏感仓库内容。
